# webhook-hub

Единая точка приёма вебхуков от телефонии, мессенджера и почтового шлюза с нормализацией
разнородных событий в одну модель. Pet-проект, не рассчитан на прод-нагрузку как есть -
ниже отдельно расписано, что для прода пришлось бы дорабатывать.

Проект накладывается поверх стандартного скелета `laravel new` - composer.json, .env.example
и прочие файлы фреймворка не переписаны, добавлен только доменный код. Каталог `vendor` в
архиве отсутствует, ставится через composer.

## Таблицы

`inbound_events` - сырое событие как оно пришло: источник, external_id для дедупликации,
JSON-payload, флаг валидности подписи, статус обработки и время приёма/обработки. По паре
(source, external_id) стоит уникальный индекс, приём делается через upsert, поэтому повторная
доставка от источника не плодит дубли, а просто обновляет запись. Payload хранится в JSON-колонке -
для очень крупного письма с вложениями возможны ограничения MySQL/MariaDB по размеру строки,
для pet-проекта это не решалось, в проде тело крупнее нескольких сотен килобайт стоит уносить
в файловое хранилище и оставлять в базе только ссылку.

`normalized_events` - результат нормализации: тип события (call_started, call_ended,
message_received, email_received), subject - человекочитаемая подпись события для журнала
(номер звонящего, тема письма), контактное значение (телефон или email), тело, метаданные
в JSON и ссылка на исходное inbound-событие. Одна запись на одно inbound-событие, что даёт
идемпотентный replay.

`contacts` - справочник контактов по телефону и email. Резолвится в job'е при обработке:
если контакт найден по телефону или email, недостающие поля дозаполняются, иначе создаётся
новый. Явная полиморфная связь с событиями не сделана - у нас только один тип владельца
(normalized_events), поэтому обычный внешний ключ проще и честнее, чем morph-таблица ради
одного потребителя. Если контакт уже существует и пришедший email/телефон отличается
от сохранённого - существующее значение не перезаписывается, только пустые поля дозаполняются.
Смена контактных данных - отдельная операция, не вебхук.

`tasks` - создаются автоматически по правилу: звонок завершился (call_ended), длительность
больше нуля и у контакта уже есть email в базе. Такая штука типична для CRM: если звонок
не пустой и контакт нам знаком, ставим себе напоминание.

## Как это работает

POST на `/webhook/{source}` сначала проходит троттлинг (`throttle`, лимит в
`WEBHOOK_RATE_LIMIT`, по умолчанию 60 запросов в минуту с одного IP на маршрут), затем
middleware `VerifyWebhookSignature`, которая берёт адаптер источника из
`WebhookAdapterRegistry` и проверяет подпись. Если подпись битая - сразу 401 и запись
в `inbound_events` с `signature_valid = false`, без постановки в очередь. Запись и там,
и там (успех/неуспех) идёт через один сервис `InboundEventRecorder::record()` - раньше
одинаковый upsert был продублирован в middleware и контроллере, теперь общая точка.

Job (`ProcessInboundEvent`) резолвит адаптер, вызывает `normalize()`, резолвит контакт
и создаёт/обновляет `normalized_events`, применяет правило создания задачи, помечает
`inbound_events` как обработанное. Всё внутри одной транзакции. Джоба помечена
`ShouldBeUnique` по `inbound_event_id` на 5 минут - если один и тот же inbound_event_id
попадёт в очередь дважды (повторная доставка вебхука почти одновременно с replay),
второй диспатч не встанет в очередь параллельно первому. `backoff()` разносит три попытки
на 10/30/60 секунд вместо мгновенного повторного удара по базе при сбое.

Три источника - три адаптера (`TelephonyAdapter`, `MessengerAdapter`, `EmailAdapter`),
реализующих `WebhookAdapterContract`. Регистрируются в `WebhookAdapterServiceProvider`,
добавить новый источник - значит написать адаптер и зарегистрировать его, роуты и middleware
трогать не надо.

Заголовок почты называется `X-Email-Signature`, не `X-DKIM-Signature` - внутри HMAC общим
секретом почтового шлюза, а не настоящий DKIM. Настоящий DKIM - это асимметричная подпись,
публичный ключ для которой публикуется в DNS TXT-записи домена отправителя; воспроизводить
это в pet-проекте избыточно, но называть HMAC чужим именем не стоит, чтобы не вводить в
заблуждение при реальной интеграции.

Резолвинг контакта (`ContactResolver`) специально различает subject события и имя контакта:
для звонка это номер телефона, для письма - тема письма, и ни то ни другое не является именем
человека. Имя контакта заполняется только если источник его реально передаёт - `sender_name`
у мессенджера или `from_name` у письма (если шлюз его прокидывает отдельным полем из
"From: Имя <email>"). Из-за этого поле `subject` в `normalized_events` и параметр
`contact_name`, который уходит в `ContactResolver`, - это два разных значения, а не одно
и то же под разными именами.

Резолвер также ловит гонку: если два воркера одновременно не находят контакт по телефону/email
и оба пытаются его создать, один упадёт на unique-констрейнте (SQLSTATE 23000) - тогда вместо
падения джобы резолвер просто ищет контакт ещё раз. Без этого джоба просто ретраилась бы
(`tries = 3`) и на второй попытке находила существующий контакт, но с лишней ошибкой в логах
на каждый такой случай.

Страница `/events` отдаёт статичный Blade-шаблон, вся динамика - через `fetch` к
`/events/data` (фильтры, сортировка, пагинация) и `/events/{id}` (карточка события).
Обновление списка каждые 5 секунд через `setInterval`, без вебсокетов - для журнала
вебхуков это избыточно. Весь текст, который приходит от внешних систем (payload, external_id,
нормализованная форма), перед вставкой в DOM проходит через `escapeHtml()` в `events.js` -
изначально верстка собиралась через `innerHTML` с сырым `JSON.stringify()` внутри `<pre>`,
и строка вида `"</pre><script>...</script>"` в теле письма или сообщения закрывала бы тег
и выполняла код. Теперь это исключено экранированием на стороне клиента; серверная часть
данные не обрабатывает и не рендерит, только отдаёт JSON.

## Что сознательно не сделано

- `/events` открыт без авторизации. Для pet-демо это ок, для реального использования -
  либо `Route::middleware('auth')`/`auth.basic` на группу `/events*`, либо вынос за периметр
  (VPN, обратный прокси с базовой авторизацией).
- Тесты гоняются на SQLite in-memory (`phpunit.xml`), а в проде используется MySQL/MariaDB.
  `upsert` и JSON-колонки у SQLite и MySQL ведут себя не идентично, так что green-тесты не
  на 100% гарантируют то же поведение в проде. Для более честной проверки стоило бы поднимать
  MariaDB в CI и гонять тесты на ней - за рамками этого пет-проекта.
- Rate limiting сделан на уровне одного `throttle` по IP, без разделения по источникам
  или API-ключам конкретного интегратора - для нескольких клиентов на одном сервере этого
  недостаточно.

## Примеры входящих payload

Телефония, `POST /webhook/telephony`, заголовок `X-Signature: hex(hmac_sha256(body, secret))`:

```json
{
  "event": "call.ended",
  "call_id": "call-88231",
  "from": "+79261234567",
  "to": "+74951234567",
  "direction": "inbound",
  "duration": 145,
  "started_at": "2026-09-10T10:00:00+03:00",
  "ended_at": "2026-09-10T10:02:25+03:00"
}
```

Мессенджер, `POST /webhook/messenger`, заголовок `X-Webhook-Secret: <shared-secret>`:

```json
{
  "message_id": "msg-55210",
  "chat_id": "chat-991",
  "from": "+79261234567",
  "sender_name": "Иван Петров",
  "text": "Здравствуйте, подскажите статус заказа",
  "timestamp": "2026-09-10T11:15:00+03:00"
}
```

Почта, `POST /webhook/email`, заголовок `X-Email-Signature: base64(hmac_sha256_raw(body, secret))`:

```json
{
  "message_id": "<a1b2c3@mail.example.com>",
  "from": "client@example.com",
  "from_name": "Иван Клиентов",
  "to": "support@company.com",
  "subject": "Вопрос по договору",
  "body": "Добрый день, когда ожидать ответ по счёту №4521?",
  "received_at": "2026-09-10T09:40:00+03:00"
}
```

`from_name` опционален - если шлюз его не присылает, имя контакта просто не заполнится,
тема письма туда не подставляется.

## Запуск

```
cp .env.example .env
docker-compose up -d --build
docker-compose exec app php artisan key:generate
docker-compose exec app php artisan migrate
```

Приложение поднимется на `http://localhost:8000/events`, воркер очереди - отдельным
контейнером. Секреты подписи задаются через `WEBHOOK_TELEPHONY_SECRET`,
`WEBHOOK_MESSENGER_SECRET`, `WEBHOOK_EMAIL_SECRET`, лимит запросов - через
`WEBHOOK_RATE_LIMIT` (в `.env`).

Локально без Docker - через `composer install`, MySQL/MariaDB под рукой, `php artisan migrate`,
`php artisan serve` и отдельно `php artisan queue:work`.

Переобработать конкретное событие вручную:

```
docker-compose exec app php artisan webhooks:replay 42
```

## Тесты и статический анализ

```
composer install
vendor/bin/phpunit
vendor/bin/pint
vendor/bin/phpstan analyse
```

В тестах используется sqlite в памяти и синхронная очередь (`QUEUE_CONNECTION=sync`) - это
упрощает assertions, в проде остаётся `database` драйвер с отдельным воркером. Ограничение
такого подхода описано выше, в разделе "что сознательно не сделано".
